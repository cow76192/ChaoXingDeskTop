## 二、中等问题

### M1. 打包体积严重冗余（dist 176 MB）

**证据**：`desktop/dist/ChaoxingDesktop` 共 176 MB，其中与功能无关的大文件：

| 文件 | 大小 | 说明 |
| --- | --- | --- |
| `_internal/icudt78.dll` | 31.6 MB | 经 131 个 PE 导入表扫描，无任何模块加载它 |
| `_internal/PySide6/opengl32sw.dll` | 19.7 MB | 软件 OpenGL 回退，本应用未使用 3D |
| `_internal/PySide6/Qt6Quick.dll` | 6.4 MB | QML 运行时，本应用为纯 Widgets |
| `_internal/PySide6/Qt6Qml.dll` | 5.1 MB | 同上 |
| `_internal/PySide6/Qt6Pdf.dll` | 4.4 MB | 未使用 PDF |
| `_internal/PySide6/translations/*.qm` | 6.7 MB | 数十种语言，仅需 zh_CN |

**原因**：`ChaoxingDesktop.spec:27` 的 `excludes` 未排除 `QtQml/QtQuick/QtSvg/QtVirtualKeyboard/QtPdf` 等模块，且 `requirements-lock.txt` 未生效（见 M2），构建环境残留了大量未被引用的包。

**影响**：便携包体积与解压时间偏大；`icudt78.dll` 属纯冗余（不构成兼容性风险——spec:33 已正确过滤 `icuuc/icuin/icu.dll`）。

**建议**：在 spec 的 `excludes` 中补充 `PySide6.QtQml`、`PySide6.QtQuick`、`PySide6.QtSvg`、`PySide6.QtVirtualKeyboard`、`PySide6.QtPdf`；过滤 `opengl32sw.dll`、`icudt78.dll` 与多余 `translations`。

### M2. 依赖锁文件从未被安装，构建不可复现

**证据**：
- `scripts/build.ps1:9` 安装的是 `requirements.txt` + `requirements-build.txt`
- `requirements-lock.txt` 仅在 `build.ps1:11` 被**生成**，从未被用于安装
- 实测：锁文件 29 条 vs 虚拟环境实装 46 条

未进入锁文件却已实装并被打入发行包的包：

```
openai, httpx, httpx2, httpcore, httpcore2, anyio, h11, sniffio,
pydantic, pydantic-core, annotated-types, typing-inspection,
truststore, jiter, socksio, tqdm
```

**影响**：`requirements-lock.txt` 声称"发布所用确切依赖记录"，但实际构建环境比它多出 17 个包。换机器重建时若只按锁文件安装，行为可能与现有发行包不一致；这 17 个包也是 M1 体积冗余的来源之一。

**建议**：`build.ps1` 改为从 `requirements-lock.txt` 安装（`pip install -r requirements-lock.txt`），使锁文件真正生效。

### M3. spec 排除名单因下划线/连字符不一致而失效

**证据**：`ChaoxingDesktop.spec:14`

```python
if name.lower().replace('_', '-') in locked_names and name.lower() not in (
        'pyinstaller', ..., 'pyside6-webengine', 'pyside6-pdf', ...):
```

右侧元组用的是**连字符**（`pyside6-pdf`），但左侧比较用的是**原始下划线名** `name.lower()`（即 `pyside6_pdf`）。两者永不相等，因此排除条件恒为假。

**实测确认**：发行包中确实存在本应被排除的元数据：

```
_internal/pyside6_pdf-6.12.0.140.dist-info
_internal/pyside6_webengine-6.12.0.140.dist-info
```

**建议**：把比较值统一规范化，例如两侧都用 `name.lower().replace('_', '-')`。

## 三、低等问题

### L1. `ProviderPicker.move()` 覆盖了 `QWidget.move(x, y)`

`desktop/chaoxing_desktop/widgets.py:37` 定义了 `def move(self, offset)`，而 `QWidget` 已有 `move(x, y)` 方法。实测：

```
p.move(10, 20)  ->  TypeError: ProviderPicker.move() takes 2 positional arguments but 3 were given
```

**当前影响有限**：Qt 布局系统内部使用 `setGeometry()`，实测把 `ProviderPicker` 放入 `QVBoxLayout` 并渲染正常。但这属于**潜伏缺陷**——任何后续代码（或 Qt 内部路径）以坐标方式移动该控件都会抛 `TypeError`。

**建议**：重命名为 `move_item(offset)`（`widgets.py:32` 的调用点同步修改）。

### L2. `gui.py` 存在未使用的导入

`desktop/chaoxing_desktop/gui.py:7` 导入 `QUrl`，但全文件无任何使用点（已用 AST 扫描确认）。

### L3. 字体资源完整性只在测试中校验，运行时不校验

`desktop/chaoxing_desktop/worker.py:214` 的断言 `assert len(fonthash_dao.char_map) > 100` 只在 `action == "probe"` 分支执行，而该分支**仅由测试脚本触发**，GUI 从不发送 `probe`。

**关联风险**：`vendor/chaoxing/api/cxsecret_font.py:100-106` 在字体表加载失败时会静默降级为空表，而 `decrypt()`（同文件 204-205 行）查不到映射时**原样返回未解密字符**。若字体资源损坏，加密题目会拿未解密文本去搜题并可能填入错误答案，且不抛异常。

> 说明：该静默降级逻辑**继承自上游**（`reference/chaoxing/api/cxsecret_font.py:104-110` 完全相同），非本项目引入。本项目已用 `probe` 断言加以防护，只是未在启动时调用。

**建议**：在真实任务启动前调用一次 `probe` 等价校验（或把 `worker.py:214` 的断言移入 `load_core`），失败时明确提示用户而非静默降级。

### L4. `requirements.txt:9` 声明了未被使用的 `chardet`

全树（`chaoxing_desktop/`、`vendor/`）无任何 `chardet` 导入，但 `chardet-5.2.0.dist-info` 仍被打入发行包。

### L5. loguru 占位符误用导致日志丢失

`vendor/chaoxing/api/base.py:746-747`：

```python
logger.error("请求url:", resp.url)
logger.error("请求头：", dict(_session.headers) | headers)
```

loguru 使用 `{}` 占位符，无占位符时多余参数被静默丢弃。实测确认：

```
logger.error("comma-style:", "https://example.test/x")   ->  CAPTURED: comma-style:
logger.error("brace-style: {}", "https://example.test/x") ->  CAPTURED: brace-style: https://example.test/x
```

**对比**：同文件 741-742 行的 403 分支写法是正确的 `"请求url: {}"`。因此仅在"未知错误"分支会丢失排障信息。

### L6. 死代码与残留

| 位置 | 问题 |

## 四、经实测证伪的怀疑（请勿据此修改代码）

以下 4 项在检查过程中曾被怀疑为缺陷，**均已通过实验证伪**。记录于此以避免后续重复排查或误改。

### ✗ 证伪 1：`desktop/tests` 有 3 项测试失败

在沙箱内运行 `python -m unittest discover -s tests -p 'test_*.py'` 会得到 `FAILED (failures=1, errors=2)`，涉及 `test_worker.py` 的三个用例。

**实测证伪**：全部失败均由同一环境原因造成——沙箱拒绝 `os.chdir` 进入 `tempfile.mkdtemp()` 创建的目录：

```
mkdtemp: ...\_tmptest\probe-1_y_pet4   mode: 0o40777
chdir FAILED: PermissionError [WinError 5]
chdir into plain mkdir OK
```

这三个用例都通过 `TemporaryDirectory()` 传递 `data_dir`。**与项目代码无关**；同时手动执行 worker 演示流程正常（3 门演示课程、协议正确）。测试记录中声称的 47 项通过数量与树内用例数一致。

### ✗ 证伪 2：打包后字体资源路径失效

曾有分析认为 `spec` 把 `vendor/chaoxing` 作为 `pathex`，导致冻结模块的 `co_filename` 为 `api\cxsecret_font.py`，其 `resource_path()` 会解析到不存在的 `_internal\resource\`，从而使"字体资源加载通过"的验收在其他机器上不成立。

**实测证伪**（决定性实验）：
1. 把整个 `dist/ChaoxingDesktop` 复制到无关路径（`_tmptest\relocated\App`）运行 probe → `font_entries: 30884`，正常；
2. 在该副本中把 `_internal\vendor\chaoxing\resource\font_map_table.json` 改名后重跑 → 报错信息明确指向**副本自己的**该文件：

```
初始化字体哈希数据失败 - 加载字体映射表失败:
  ...\relocated\App\_internal\vendor\chaoxing\resource/font_map_table.json
AssertionError: 字体资源缺失
```

说明打包程序读取的正是自身 `_internal\vendor\chaoxing\resource\` 下的文件，**发行包是自包含的**，验收记录成立。

### ✗ 证伪 3：spec 的 `datas` 目标目录错位

曾有分析认为 `file.relative_to(root/'vendor/chaoxing').parent` 丢失顶层目录，会把 `api/*.py` 与字体表放到 `_internal\api\`、`_internal\resource\`。

**实测证伪**：发行包中实际布局为

```
_internal\vendor\chaoxing\api\*.py
_internal\vendor\chaoxing\resource\font_map_table.json
```

且 `_internal\api`、`_internal\resource` **均不存在**。`datas` 目标拼接正确。

### ✗ 证伪 4：`plans/Windows桌面版开发计划书.md` 编码损坏

曾有分析称该文件为 GBK 编码导致乱码。

**实测证伪**：首字节 `23 20 E8 B6 85 ...`，以严格 UTF-8 解码器校验**通过**，是合法 UTF-8。个别工具显示异常属其自身编码探测问题。
